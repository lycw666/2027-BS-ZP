# 技术路线与系统实现方案

## 一、总体设计

本课题设计并实现一个基于 ESP32 的多节点智能环境监测与可靠通信系统。

系统采用分层设计，包括环境数据采集层、MQTT 通信层、服务端处理层、数据库存储层和 Web 应用层。

开发初期使用 Python 模拟两个独立物联网节点，验证系统通信和可靠性机制；完成基础功能后，将模拟节点逐步替换为真实 ESP32 硬件节点。

系统重点解决网络中断情况下的数据缓存、自动重连和数据补传问题。

## 四、节点数据采集与消息格式

系统初期设置两个独立节点：

- Node001：环境监测节点1。
- Node002：环境监测节点2。

每个节点按照设定的采集周期产生环境数据，并通过 MQTT 发送至服务端。

每条消息必须包含以下基本字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| node_id | String | 节点唯一标识 |
| seq | Integer | 节点消息递增序号 |
| timestamp | String | 数据采集时间 |
| temperature | Float | 温度 |
| humidity | Float | 湿度 |
| light | Float | 光照强度 |

消息格式示例：

```json
{
  "node_id": "Node001",
  "seq": 1001,
  "timestamp": "2026-11-01T17:00:00",
  "temperature": 25.6,
  "humidity": 61.2,
  "light": 350
}
```

其中，node_id 用于区分不同节点，seq 用于识别消息顺序和重复消息，timestamp 用于计算数据传输时延。

## 五、MQTT通信设计

系统采用 MQTT 协议实现多节点与服务端之间的通信。

初期使用 Mosquitto 搭建 MQTT Broker，Python 节点通过 Paho MQTT 客户端发布环境数据，服务端订阅节点数据主题。

计划采用以下主题结构：

| MQTT主题 | 作用 |
|---|---|
| aiot/node/Node001/data | Node001环境数据 |
| aiot/node/Node002/data | Node002环境数据 |
| aiot/node/+/data | 服务端订阅所有节点数据 |
| aiot/node/+/ack | 服务端向节点确认数据 |
| aiot/node/+/control | 服务端向节点发送控制命令 |
| aiot/node/+/status | 节点状态信息 |

第一版采用 MQTT QoS 1 作为基础通信等级。

后续根据实验情况开展不同 QoS 等级的通信性能比较。

## 六、可靠通信机制设计

本课题重点设计断网缓存、自动重连和数据补传机制。

### 6.1 断网检测

节点定期检查 MQTT 连接状态。

当检测到连接中断时，进入离线状态，并继续产生环境采集数据。

### 6.2 RAM数据缓存

节点使用 RAM 队列暂存断网期间产生的数据。

每条缓存数据保留 node_id、seq、timestamp 和环境采集值。

当网络恢复后，按照消息序号从小到大的顺序进行补传。

第一版使用内存队列实现，后续可考虑增加 Flash 或 LittleFS 持久化缓存。

### 6.3 自动重连

当 MQTT 连接断开时，节点自动尝试重新连接。

采用逐步增加重试间隔的方式，避免频繁连接请求造成额外通信负担。

网络恢复后重新建立 MQTT 连接，并恢复正常数据传输。

### 6.4 数据补传

网络恢复后，节点依次发送缓存队列中的历史数据。

服务端接收到消息后进行数据校验，并根据 node_id 和 seq 判断消息是否已经存储。

采用数据库唯一约束保证重复消息不会产生重复记录。

### 6.5 数据确认与缓存清理

服务端完成数据库写入后，通过 MQTT ACK 主题返回应用层确认消息。

节点收到对应消息的确认后，才将该条数据从缓存中移除。

如果没有收到确认，则保留该数据，后续重新发送。

通过上述机制降低网络异常和消息重复发送造成的数据丢失风险。

## 七、数据库设计

第一版采用 SQLite 数据库。

主要建立以下数据表：

### 7.1 环境数据表

| 字段 | 说明 |
|---|---|
| id | 数据主键 |
| node_id | 节点编号 |
| seq | 消息序号 |
| timestamp | 采集时间 |
| temperature | 温度 |
| humidity | 湿度 |
| light | 光照 |
| receive_time | 服务端接收时间 |

其中 node_id 和 seq 建立联合唯一约束，用于实现重复消息过滤。

### 7.2 设备信息表

保存设备编号、设备名称、设备类型、在线状态及最后通信时间。

### 7.3 报警记录表

保存报警节点、报警类型、报警内容、发生时间和处理状态。

## 八、Web监测平台设计

Web平台主要实现以下功能：

1. 实时监测：显示各节点最新温度、湿度和光照数据。
2. 设备管理：显示节点编号、设备名称和在线状态。
3. 历史查询：根据节点编号和时间范围查询历史环境数据。
4. 数据可视化：使用 ECharts 展示温湿度和光照变化曲线。
5. 异常报警：环境参数超过设定阈值时产生报警记录。
6. 远程控制：支持向指定节点发送基本控制命令。

## 九、实验设计与性能评价

通过正常通信实验、断网恢复实验和多节点性能实验评价系统可靠性。

### 9.1 正常通信实验

使用两个节点同时发送环境数据，验证 MQTT 通信、服务端接收和数据库存储功能。

### 9.2 断网恢复实验

分别设置 10 秒和 30 秒网络中断，每种情况至少进行三轮测试。

记录断网期间产生的数据量、缓存数量、网络恢复时间和实际补传数量。

### 9.3 性能评价指标

| 指标 | 评价内容 |
|---|---|
| 数据完整率 | 预期产生的数据中最终成功入库的比例 |
| 重连时间 | 网络恢复到 MQTT 连接重新建立的时间 |
| 补传成功率 | 待补传数据中最终成功入库的比例 |
| 端到端时延 | 数据采集到服务端接收的时间差 |
| 消息吞吐量 | 单位时间内服务端成功接收的消息数量 |

### 9.4 多节点扩展实验

在基础两个节点的基础上，逐步增加至五个和十个模拟节点。

比较不同节点数量下的消息接收情况、通信时延和系统运行表现。
